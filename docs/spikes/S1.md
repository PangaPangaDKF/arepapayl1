## 6. Problems hit
1. **Wrong CLI path in the brief.** `~/.avalanche-cli/bin/avalanche` is **v1.2.4** (2023; no `blockchain` command). The v1.9.6
   binary is `~/bin/avalanche`, which is first on PATH. The scripts use `~/bin/avalanche` (override with `AVALANCHE_BIN`).
2. **`warp cannot be activated before Durango`.** My first genesis set `warpConfig.blockTimestamp: 0`. The chain was created on
   the P-Chain but the VM refused to start, and the CLI bootstrap timed out.
   - Fix: warp's `blockTimestamp` = genesis timestamp (`1794719266`), as the CLI template does. The allowlists and feeManager
     keep `0`, which is fine.
   - Cleanup touched only arepapaybank: `avalanche node local destroy arepapaybank-local-node-local-network`, `blockchain
     create --force`, then redeploy.
   - The broken first subnet (`2W9boARg…`, chain `kLwvZVd2…`) is inert garbage on the local P-Chain.
   - I deliberately did **not** run `avalanche network clean`. It drops local deployment info from every sidecar, which would
     have modified the v1 `ArepaPay` config.
3. **The CLI's PoA bootstrap needs a tx-allowlisted sender.** The CLI signs `initializeValidatorSet` (and later PoA validator ops)
   with ewoq. That's why ewoq is in `txAllowList.enabledAddresses`, a deviation from "enabled: nothing else yet".
   - ewoq is *not* a txAllowList admin and *not* a deployer.
   - On Fuji, this role moves to the validator-manager owner (Safe).
4. **Deployer allowlist semantics.** A blocked deploy is not rejected at the RPC. When gas is preset, it is included and fails
   with status 0, and the fee is still charged. Only `eth_estimateGas`/`eth_call` show the reason (`tx.origin … is not authorized
   to deploy a contract`). Apps should simulate first.
5. **`requirePrimaryNetworkSigners: true`** in warp is the CLI default. Keep it in mind for S6: messages from the L1 to C-Chain
   are verified with the L1's validator set; this flag affects messages *from the Primary Network*.
6. **v1 state.**
   - `~/.avalanche-cli/subnets/ArepaPay` was not read for keys and not modified (sidecar mtime is still 2026-03-22).
   - Its old local network dir `runs/network_20260322_180457` is untouched.
   - `network start` created a new network dir (`runs/network_20261115_010923`) and repointed the CLI-global
     `~/.avalanche-cli/localNetworks.json` to it. So the v1 chain is no longer the "current" local network.
7. **`chain.json`** from the CLI enables `admin`, `debug*` and `internal-personal` RPC namespaces. That's acceptable on local but
   must be trimmed before Fuji.

## 7. Moving to Fuji (stage B): what is needed

**P-Chain validator fee model (ACP-77), verified:**
- Each L1 validator prepays a P-Chain balance that is debited continuously at `price = M·exp(x/K)` nAVAX/s, where:
  - `M` = 512 nAVAX/s;
  - `x` grows only when active L1 validators exceed the target T = 10,000.
- At the minimum, that is **512 nAVAX/s ≈ 1.33 AVAX per validator per 30 days** (512e-9 × 2,592,000 = 1.327).
- When the balance reaches 0 the validator goes **inactive**. It is revived with `IncreaseL1ValidatorBalanceTx` (CLI:
  `avalanche validator increaseBalance` / `getBalance`). `DisableL1ValidatorTx` returns the remainder to the
  RemainingBalanceOwner.
- Sources:
  - ACP-77 spec: https://github.com/avalanche-foundation/ACPs/blob/main/ACPs/77-reinventing-subnets/README.md
  - Live `platform.getValidatorFeeConfig` on `https://api.avax-test.network/ext/bc/P` and `https://api.avax.network/ext/bc/P`
    (values in §5).
  - CLI help: `blockchain deploy --balance` ("AVAX balance of each bootstrap validator that will be used for continuous fee on
    P-Chain") and `blockchain addValidator --balance`.
- So ARCHITECTURE's "about 1.33 AVAX/month per validator" is **confirmed**. For 2 bank validators plus 1 ArepaPay validator,
  that is ≈ 4 AVAX/month plus the one-off create/convert tx fees (< 0.001 AVAX).

**Checklist:**
1. **Fuji AVAX on the P-Chain**, held by a key the user controls (`--key <stored>` or `--ledger`; never ewoq, never v1 keys).
   It funds the create/convert fees and each validator's balance (e.g. `--balance 2` gives about 6 weeks).
2. **Validator machine(s):**
   - avalanchego with the subnet-evm plugin (same VM version);
   - staking port 9651 reachable;
   - P-Chain sync (`--partial-sync` primary network);
   - BLS key + PoP.
   - Bank nodes would come in here with `--bootstrap-endpoints` / `--bootstrap-filepath`.
3. **New genesis for Fuji:**
   - all precompile admins and the validator-manager owner/proxy-admin owner = **Safe multisig + timelock** (N6), not EOAs;
   - remove ewoq from `enabledAddresses`;
   - keep the minter absent;
   - a fresh gas-station address controlled by the backend's keystore;
   - pick and check chain id uniqueness (77077 on chainlist);
   - consider `minBaseFee`, since the gas station pays it.
4. **Safe on the L1:** the Safe singleton/factory must be deployed on the L1, so the deployer address must be deployer-allowlisted
   and tx-allowlisted at genesis, or the contracts put in the genesis alloc. The bootstrap admin must be able to do this before
   handing over.
5. **ICM/Teleporter for S6.** I used `--icm=false` because the CLI's Teleporter deploy would be blocked by both allowlists. The
   TeleporterMessenger keyless deployer address (and the relayer's L1 key) must be tx-allowlisted, and the deployer
   deploy-allowlisted, or the messenger placed in genesis.
6. **Gateway, not public RPC:** trim `chain.json` APIs and put the node RPC behind the authenticated gateway (S1's "gateway RPC"
   part is **not** covered by this local spike).
7. Deploy: `avalanche blockchain deploy arepapaybank-fuji --fuji --key <name>|--ledger --bootstrap-filepath <validators.json>
   --balance <AVAX>`. Then rerun `s1-verify.sh` against a Fuji config file. The script reads only the config JSON, but the admin
   signer must become a Safe transaction, so the verify script needs a Fuji mode.

   whether the CLI can sign PoA ops with `--key`? Untested.
2. Gas station design:
   - The gas station needs to be **tx-allowlisted** to top up wallets. Should it be allowlisted at genesis, or by the admin as
     part of S5?
   - Should feeManager be used to lower `minBaseFee` (cheaper ops)? Or should the chain go gasless (`minBaseFee: 0`), which
     weakens spam resistance? Note that only allowlisted KYC'd wallets can send at all.
3. A blocked deploy still burns gas. Is that acceptable, or should deployer-allowlist checks be done client-side (eth_call) as
   policy?
4. The bootstrap validator's `deactivationOwner` is empty (threshold 0) in the CLI's local deploy. Who should own disable rights
   on Fuji (the bank's P-Chain multisig)?
5. Which validator set (how many bank nodes plus ArepaPay) for Fuji? It drives the monthly AVAX budget (1.33 AVAX/validator/month).
6. The local P-Chain uses minPrice 1 nAVAX/s. Do we need a tmpnet with mainnet-like fee params to rehearse balance top-ups?
