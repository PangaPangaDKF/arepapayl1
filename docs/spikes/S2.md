# Spike S2: eERC converter mode on the local `arepapaybank` L1

Status: **PASS** for steps 1–6 on the local L1. The phone proof measurement is **still open**: it needs the user's phone (§8).
Date: 2026-11-15. Run by a sub-agent for BRAIN.

Go/no-go hint: **at risk.** A desktop browser takes a median **7.6 s** to make one transfer proof with snarkjs. A low-end
Android phone will very likely take more than 10 s with the same browser prover (§7).

> **Key warning (N6):** every key here is **LOCAL-TEST-ONLY**.
> - The admin is `arepapay-local-admin` from S1. The script reads it from `~/.avalanche-cli/key/`; it is never printed or written.
> - The other EVM keys (alice, bob, merchant, auditor, eve, safeOwner) and every BabyJubJub key exist only in the script's
>   memory and were gone when it exited.

> - The phone-bench sample inputs (`$EERC_DIR/s2-phone/inputs/*.json`) contain throwaway BabyJubJub test keys made only for

## 2. Reproduce
The eERC source is third-party and not vendored. It is a clone of `ava-labs/EncryptedERC@8dc98cd` in `$EERC_DIR`; the default
is the scratch copy `/tmp/claude-1000/-home-panga/9175df3d-cd88-4613-9f2f-8bb72c0ae070/scratchpad/s2/eerc`.

```bash
# one-time: prepare the clone (the upstream postinstall is skipped on purpose, see problem 1)
cd $EERC_DIR && npm install --ignore-scripts && npx hardhat compile      # 737 packages, solc 0.8.27

# from the repo root (the L1 from S1 must be running; check with: cast block-number -r <rpcUrl from config/l1/arepapaybank.local.json>)
scripts/eerc/s2-run.sh              # full flow (≈1 min 46 s); rewrites config/l1/eerc.local.json

scripts/eerc/s2-phone-bench.sh      # builds + serves the phone page on :8088 (needs `bench` once for the sample inputs)
```

Each run of `s2-run.sh` deploys a fresh set of contracts; the earlier ones stay on chain unused.

Files:
- `scripts/eerc/s2-run.sh`: the entry point.
  - It copies the TS files into `$EERC_DIR/scripts/arepapay/`, so the clone's `node_modules` resolve.
  - It writes the 20-line `S2Forwarder.sol` (embedded in the script) into `$EERC_DIR/contracts/arepapay/` and compiles it.
  - It runs everything with `ts-node`.
- `scripts/eerc/s2-common.ts`:
  - BabyJubJub keygen, the same as `test/user.ts`;
  - snarkjs `groth16.fullProve`, timed;
  - input builders ported from `test/helpers.ts` (registration, transfer, withdraw);
  - PCT decryption;
  - metadata encrypt/decrypt in the same byte format as `src/metadata.ts`, re-implemented because that file imports `hardhat`.
- `scripts/eerc/s2-converter.ts`: the on-chain flow, visibility proof, gas and latency table, and the config writer.
- `scripts/eerc/s2-bench.ts`: the offline benchmark. It also writes the phone sample inputs.
- `scripts/eerc/s2-phone-bench.sh`: the static phone page (snarkjs.min.js + the same wasm/zkey), served by `python3 -m http.server`.

Things used from the clone:
- `node_modules`: ethers 6.13.4, snarkjs 0.7.5, maci-crypto, @zk-kit/baby-jubjub, poseidon-lite, ts-node;
- `src/jub`, `src/poseidon`;
- `circom/build/{registration,transfer,withdraw}/*.wasm|*.zkey`;
- the compiled `artifacts/`.

Every value is read from the generated `config/l1/arepapaybank.local.json` (rpcUrl, chainId, admin, txAllowList address).

## 5. Who can see what (proven on chain, §4 block [6])

| Data | How it appears on chain | Receiver key | Auditor key | Third registered user (eve) |
|---|---|---|---|---|
| Sender / receiver of a private transfer | `PrivateTransfer(from, to, auditorPCT, auditorAddress)`, **addresses in clear** | sees | sees | **sees** (it's just a log) |
| Transfer amount | `ReceiverPCT` (in the proof's public signals, calldata), `auditorPCT` (event) | **decrypts** (3.00, 2.00, 1.00, 0.40) | **decrypts** (same values) | **fails** (Poseidon auth check throws) |
| Balance | ElGamal `eGCT` from `balanceOf` | owner decrypts (merchant 0.40) | not directly (only the sum of auditor PCTs) | **fails** (the decrypted point is not v·G for any v in 0..20.00) |
| `message` (transfer overload) | `PrivateMessage` event; `messageType` = `PRIVATE_TRANSFER` and from/to in clear; the body is opaque bytes | **decrypts** (`intent:SPLIT-0001 part 1/2`) | **cannot**, unless the sender also encrypts it to the auditor (see finding 2) | **fails** |
| Deposit amount | `Deposit(user, amount, dust, tokenId)`, **plaintext**, plus the ERC-20 `Transfer` | — | — | sees (10.0 tUSD) |
| Withdraw amount | `Withdraw(user, amount, …)`, **plaintext** (eERC units) | — | — | sees (5.00) |

Findings that matter for the design:

1. **Deposit-only balances are not confidential.** `_convertFrom` encrypts deposits with fixed randomness 1 (comment in
   `EncryptedERC.sol` `_convertFrom`). Together with the public `Deposit`/`Withdraw` amounts, anyone can compute a balance that
   has only seen deposits and withdrawals. Confidentiality starts with the first private transfer received. That is acceptable
   (deposits are public anyway), but the app copy must not imply otherwise (T1/N5).
2. **The `message` is whatever bytes the sender passes.**
   - Here it was encrypted to the **receiver's** key, in the SDK's `encryptMetadata` format. The receiver reads it; eve cannot.
   - By construction, the auditor cannot read it either (not run separately: the auditor's key is just another wrong key, like
     eve's).
   - If the auditor or the Split Pay service must read the intent id, the client must also encrypt it to them, or send it in
     plaintext. This corrects eERC skill §1, which says "message: visible to the auditor".
   - **For BRAIN:** consider updating the skill.
3. **A contract account is not frozen by txAllowList.**
   - The `S2Forwarder` has txAllowList role 0 and still registered and transacted. The precompile checks only `tx.origin`.
   - So "freeze = remove from txAllowList" (ARCHITECTURE L4) freezes a Safe only by removing **every EOA that can execute for
     it**: its signers, plus any relayer or module.
   - Worth one line in L4 and in SPLIT_PAY_C.
4. Transfer gas is about **1.0–1.14 M**. With the 8 M block gas limit and 2 s blocks, that means **at most about 7 private
   transfers per block, about 3.5 per second** for the whole L1. Raise the gas limit before production if more is needed
   (feeManager admin).

## 7. Go / no-go against the kill criterion "proofs > 10 s on median phones"
- **Registration (one-off):** about 1 s in desktop Chrome. Even 10× slower is fine. **GO.**
- **Withdraw:** about 4 s in desktop Chrome. A low-end phone at 3–6× slower gives about 12–25 s. **Borderline / likely over**,
  but withdraw is rare (cash-out).
- **Transfer (the payment itself):**
  - About **7.6 s in desktop Chrome** on a 4-core i5. Low-end Android phones (Cortex-A53/A55-class) are typically **3–8×
    slower** than this CPU in single-thread WASM. That projects to roughly **25–60 s**.
  - It also needs a 14.4 MiB zkey download, cached after the first payment.
  - **Expected verdict for the browser/WebView snarkjs prover: NO-GO** (> 10 s).
- This is a **projection, not a measurement.** The decision waits for the phone numbers from §8.

Ways forward if the phone confirms it (for BRAIN/user to choose; none was tested here):
- a **native prover** on the phone (rapidsnark through mopro or a React Native module, or gnark through gomobile), usually
  several times faster than snarkjs WASM;
- a smaller or optimised transfer circuit (upstream work);
- UX that hides latency, such as pre-loading the zkey and starting the proof when the amount is typed. This does not change
  the criterion.
- Server-side proving for users is **not** acceptable, because the user's key would leave the device (self-custody, ARCHITECTURE
  L3). It is fine for the bank-run escrow account (Split Pay C), where a server holds that key by design.

## 8. Phone measurement: exact steps for the user (low-end Android)
1. On the PC, from the repo root, run `scripts/eerc/s2-run.sh bench 1`. This writes the sample inputs, which use throwaway test
   keys.
2. Run `scripts/eerc/s2-phone-bench.sh`. It serves `$EERC_DIR/s2-phone` on port 8088. Leave it running.
3. Connect the phone. The simplest way is USB:
   1. Turn on Developer options → USB debugging on the phone. Install Android platform-tools (`adb`) on Windows.
   2. Connect the cable. In Windows PowerShell: `adb devices`, then `adb reverse tcp:8088 tcp:8088`. WSL2 forwards Windows
      `localhost:8088` to the WSL server.
   3. On the phone, open **Chrome** at `http://localhost:8088`. `localhost` is a secure context, so WASM and workers behave
      normally.
   - Without USB: enable WSL mirrored networking, or on Windows run
     `netsh interface portproxy add v4tov4 listenport=8088 connectaddress=<WSL IP> connectport=8088` and allow TCP 8088 in the
     firewall. Then open `http://<PC LAN IP>:8088` from the phone on the same Wi-Fi.
4. Prepare the phone: charge it above 50% on the charger, close other apps, keep the screen on, use Chrome (not Samsung
   Internet), and don't touch it during the runs.
5. Set runs = 5 and press **Run registration + transfer + withdraw**. Each circuit does one warm-up, then 5 timed runs.
   Downloads are excluded from the timing but logged.
6. Send BRAIN:
   - the final `RESULT {...}` line (median ms per circuit, user agent, cores);
   - the phone model, chipset and RAM;
   - a second run of the transfer numbers, to see thermal throttling.
7. Repeat on a second "median" phone if available. The criterion is the **median phone's transfer median**: ≤ 10 s is GO,
   > 10 s is NO-GO for the browser prover, so evaluate a native prover.
8. Stop the server with Ctrl-C.

## 9. Problems hit
1. **The upstream `postinstall` would break key/verifier consistency.** `npx hardhat compile & npx hardhat zkit make --force &&
   npx hardhat zkit verifiers` recompiles every circuit and runs a **new** Groth16 setup (it downloads circom 2.1.9 and ptau).
   That writes fresh `contracts/verifiers/*` that don't match the shipped `circom/build` zkeys used by `contracts/prod`.
   - I used `npm install --ignore-scripts` + `npx hardhat compile`, with the prod verifiers and the shipped zkeys, as the
     upstream `deploy-converter.ts` does with `isProd=true`. I checked that they match (§2).
   - Production needs its own decision on whose trusted setup to trust (open question 1).
2. `src/metadata.ts` imports `ethers` from `hardhat`, so it can't run outside a Hardhat runtime. I re-implemented
   `encryptMetadata`/`decryptMetadata` in the same byte format, about 30 lines in `s2-common.ts`.
3. The upstream `deploy-converter.ts` makes an 18-decimal ERC-20 and uses hardhat signers. I followed its order (verifiers →
   BabyJubJub → Registrar → EncryptedERC with the library linked) in ethers directly, against the L1 RPC, with a 6-decimal
   token. 10.00 tUSD = 10,000,000 raw → 1,000 eERC units (2 dp), dust 0.
4. Measurements ran while another agent was running `npm install` (load average 4–7). The transfer median moved from 6.5 s to
   4.4 s between the two Node runs. Repeat on an idle machine before quoting a final desktop number.
5. A Safe was not used. Deploying the Safe singleton, factory and proxy needs more allowlisted deploys and Safe tx signing.
   `S2Forwarder` (owner-only `execute(target, data)`) is functionally a 1-of-1 Safe `execTransaction`. eERC sees only
   `msg.sender` = the contract, so a Safe behaves the same. A real t-of-n Safe is SPLIT_PAY_C §5 step 3 work.
6. Not tried: the Go/gnark prover in `zk/`. It has its own setup and keys, so its own verifiers, and needs toolchain go1.24.1
   (installed: 1.22.2). It is the candidate for the bank's escrow service and possibly for native mobile proving.
